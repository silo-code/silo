# 0036. Unified update UI, in-app changelog, and skip-version

## Context

Silo has three places a user can check for updates — the macOS "Silo" app
menu, the Windows/Linux "Help" menu, and the command palette — and all three
already share one `UpdateService` singleton
(`packages/extension-host/src/extension-host/update-service.ts`), but present
its result three different ways:

- The menu items call `checkForUpdatesInteractive()`, which reports via
  native OS dialogs (`ask()`/`message()` from `@tauri-apps/plugin-dialog`).
- The status-bar "Update Silo" link opens an in-app React modal
  (`UpdatePrompt.tsx`, owned by the `core.updates` extension).
- The command palette's `core.updates.check` command reports via a toast
  (`ctx.ui.notify`).

This isn't three independent implementations drifting apart — it's one
check with three presentation layers, and the divergence is architectural,
not accidental: `menu-items.ts` lives in `extension-host` (the host layer),
which `extensions-core` depends on, not the reverse. The host cannot import
`UpdatePrompt.tsx` without inverting that boundary, so the menu path was
built against native dialogs instead.

Separately, the existing modal has no way to show _why_ an update might be
worth taking (no changelog) and no way to defer a specific version
permanently — only an ephemeral "Later" that reappears on the next check.

## Decision

**Unify all three entry points on one presentation policy**, dispatched
through the extension command system rather than by importing across the
package boundary: `menu-items.ts` already calls other extension-backed menu
items via `executeCommand(item.command)` (`./commands`); the two
"Check for Updates…" items switch from `checkForUpdatesInteractive()` to
`executeCommand("core.updates.check")`, the same command the palette already
registers. `checkForUpdatesInteractive` and its native-dialog code path are
deleted outright — no other callers exist. Post-unification, that one command
means: open the in-app modal when `phase === "available"`; show a toast for
`upToDate`/`error`; do nothing for `checking`. No new command id was added
for this — after the behavior change, a `checkAndPrompt` command would be
identical to the existing `check` command, so the existing id was reused
rather than duplicated.

**The modal gains two new pieces:**

1. **A changelog**, showing every release note between the installed and
   available version (not just the latest), sourced from a new
   `changelog.json` — generated by extending
   `apps/docs/scripts/copy-changelog.mjs` to parse
   `apps/desktop/CHANGELOG.md`'s `## [x.y.z](url) (date)` sections into
   `{ version, date, body }` entries, published as a static asset at
   `apps/docs/public/changelog.json` (served at
   `https://getsilo.dev/changelog.json`). Chosen over extending
   `apps/update-server` because the docs pipeline already regenerates this
   content on every build with no release-time CI step to add — the update
   server, by contrast, only becomes involved on the critical path of
   actually shipping a release, which is a riskier place to bolt on new
   logic. The app fetches and ETag-caches this JSON (same pattern as
   `registry-client.ts`'s `fetchRegistryIndex`), slices the range between the
   installed and available version, and falls back to the single-version
   `notes`/`body` field already present on the Tauri updater manifest (fetched
   today, but previously unread anywhere in the app) if the fetch fails or
   the range comes back empty.
2. **"Skip this version"**, distinct from the existing "Later": Later stays
   ephemeral (closes the modal, no persistence, reappears next check).
   "Skip this version" persists the skipped version string via
   `ctx.storage.global` (the extension's own cross-workspace key/value store)
   and suppresses the status-bar link for that version specifically — the
   link reappears automatically once a _newer_ version is available, compared
   via the existing string-based `compareVersions` from `registry-client.ts`
   (re-exported through the internal barrel for this purpose; note this repo
   has a second, incompatible `compareVersions` in `engine-compat.ts` that
   operates on parsed version triples for engine-constraint checks — the two
   are not interchangeable). A manual "Check for Updates" (menu or palette)
   always bypasses skip and shows the real result — skip only ever silences
   the passive, unprompted surface. No "undo a skip" UI exists; the manual
   check is the deliberate escape hatch.

**Update-choice analytics** extend the existing ADR 0031 pipeline
(`apps/update-server`, GoatCounter site `silo-updates`) with a new
`/update-action/<action>/<channel>/<version>` route, reporting `installed`,
`skipped-version`, and `skipped-later` as distinct events (not collapsed into
one "skipped") so skip-rate and defer-rate stay distinguishable in the data.

## Consequences

**Easier:**

- One presentation policy to maintain instead of three; a future change to
  the update-available UI only needs to touch `UpdatePrompt.tsx`.
- Dave (and users) can see what actually changed before deciding to update,
  instead of updating blind or avoiding updates out of uncertainty.
- A user who deliberately doesn't want a specific release stops being nagged
  about it without losing future updates.

**Harder:**

- `changelog.json` is a second, independently-versioned representation of
  `CHANGELOG.md`'s content (alongside the existing Markdown copy at
  `/changelog`) — a future change to the changelog's Markdown _shape_
  (heading format, compare-URL structure) needs updating the parser in
  `copy-changelog.mjs` too, or the JSON silently stops matching.
- `apps/update-server` now has a second route and a second reason to be
  touched, on top of ADR 0031's existing operational surface
  (`GOATCOUNTER_TOKEN` rotation, no CI/CD).
- The app now makes one deliberate, user-action-triggered network call it
  didn't make before (`update-action` reporting). See Alternatives below for
  why this doesn't reopen ADR 0031's rejection of client-side telemetry.

**Neutral / committed to:**

- `checkForUpdatesInteractive` and the native-dialog path are gone for good —
  any future "must look native" requirement for the menu path would need to
  be reintroduced deliberately, not just restored, since the underlying
  dialog-plugin usage is deleted, not merely unused.
- Skip state lives in `ctx.storage.global`, which is per-channel by
  construction (stable and nightly write to separate config directories per
  ADR 0024) — a version skipped on stable has no effect on nightly, and vice
  versa, with no extra code needed to enforce it.

## Alternatives considered

**A. Keep native dialogs for the menu, only enhance the status-bar modal.**
Rejected — this was the starting point Dave flagged as confusing (three
different UIs for one underlying check), and native dialogs can't show a
changelog or three action buttons regardless.

**B. Have the app call the GitHub Releases API directly for changelog
range data.** Rejected. Release-please does create real GitHub Releases with
notes bodies, so this is mechanically possible, but there is no existing
precedent anywhere in this codebase for the desktop app calling
`api.github.com` at runtime — every other runtime data need
(`registry.getsilo.dev`, the updater manifest itself) goes through a
Silo-controlled domain instead, almost certainly to avoid unauthenticated
GitHub's 60-requests/hour-per-IP cap across every desktop install sharing a
NAT or office network. Embedding a token in a shipped binary to raise that
limit is its own, worse problem. Serving `changelog.json` from
Silo-controlled infrastructure keeps that precedent intact.

**C. Bundle the full changelog with the app binary instead of fetching it.**
Rejected. `CHANGELOG.md` is small (~47KB) so size isn't the issue, but the
_installed_ binary's bundled copy necessarily predates the very entries the
modal needs to show — the whole point is displaying what changed _between_
the installed version and a release that didn't exist yet when the installed
binary was built. This only works as a live fetch.

**D. Skip the `update-action` analytics event; reuse ADR 0031's posture of
"never add client-side telemetry code."** Considered directly, given ADR
0031's Alternative B explicitly rejected "a client-side telemetry SDK in the
app" specifically because it wanted no new, always-on tracking code path.
Concluded this is a different shape of change, not the same alternative
revisited: 0031 rejected _ambient, always-running_ instrumentation; the
`update-action` call here is one fire-and-forget request tied to a single,
explicit, already-visible user action (clicking Install or Skip in a modal
the user opened), not a background SDK. It's additive to, not a reversal of,
0031's actual constraint (no persistent identifiers, no always-on collection)
— which this still fully respects. Flagged for Dave explicitly before
deciding to proceed this way.

**E. Register a second command (`core.updates.checkAndPrompt`) instead of
reusing `core.updates.check`.** Deferred, not rejected — floated during
planning as the more explicit name, but once the palette's `check` command
adopts the unified prompt-or-toast behavior, a second command with identical
behavior would be pure duplication. Revisit if the two entry points' behavior
is ever meant to diverge again (e.g., a palette-only "silent check" that
never opens a modal).
